# Shared downloads and offline reading

This product slice adds a common Compose downloads list, gallery download action, pause/resume/delete controls and offline reading. It is under platform validation; it does not complete M4 or five-platform P0 acceptance.

`GalleryDownloadQueue` owns FIFO scheduling and one active image transfer. It uses the same 32 MiB image limit as the existing transport, validates gallery/page identities, and bounds tasks and metadata. Each active task fixes its site and authentication generation. Account actions pause shared queues; an identity change during a response cannot publish that response. Pausing stops the active worker even if storage cannot save the requested state. Restored tasks require an explicit resume.

An actual Desktop gallery repeatedly stopped after four saved pages while the online reader recovered page five with its existing retry. Downloads now use the same official `nl` replacement key once after a connection or server failure. Authentication failures, challenges, rate limits, oversized payloads and a failed replacement stop without an automatic retry loop. Every metadata/page/image request, including the replacement, checks the captured identity before and after its response. Real Ktor regressions cover both boundaries and preserve cookie isolation and referrers.

Desktop and iOS use the real platform Room driver and `RoomGalleryDownloadStorage`. The new `DownloadDatabase` is separate from `EhDatabase` version 23 and `SearchDatabase` version 2; existing Android tables, migrations and settings remain unchanged. Images are written to a private temporary file, flushed and atomically moved before their page record is committed. Page records retain SHA-256 and length; actual reads verify both. A failed progress update can be reconciled from already committed page records without fetching those images again. This does not claim a transaction spanning SQLite and the filesystem or guaranteed power-loss durability.

The `GalleryContent` contract lets the existing paged/continuous/RTL CMP reader consume actual saved bytes. Local URIs identify only a validated gallery and page, never an arbitrary filesystem path. `CachedReaderStateStore` saves an index without a service token, so returning online resolves the real token again. History is touched without replacing full gallery metadata or deleting reading progress.

Android's adapter calls the original `DownloadManager`, workers, files, labels and recovery. Its original reader handles platform-owned downloads, retaining SAF and CBZ support. The shared list uses a snapshot under the original list lock. iOS pauses the shared queue on background transition and explains that saved pages can be resumed; it does not promise unrestricted background execution. Desktop cancels and joins queue work before closing its database.

## Design reference and licensing

The previously audited Animeko `docs/contributing/architecture.md`, platform component boundary and `app/shared/app-data/.../DatabaseStorage.kt` inform separation of shared behavior from platform construction. EhViewer's queue, image protocol, original Android adapter, file/Room commit ordering and local reader contract are independently implemented. No Animeko implementation, asset, script, fixture, dependency list or video/BT behavior is copied. Existing dependency versions and the pinned AndroidX/SQLite provenance documented in `shared-history-and-data.md` are retained.

The principal targets are `core/domain/.../download/GalleryDownloads.kt`, `core/network/.../download/`, `core/data/.../RoomGalleryDownloadStorage.kt` and `database/download/`, `app/shared/.../GalleryDownloadsScreen.kt`, `GalleryCachedReaderScreen.kt` and `reader/CachedReaderStateStore.kt`, the original Android manager adapter, and the Desktop/iOS application roots.

## Validation scope

- Common queue tests cover ordering/concurrency, cancellation, late responses, failed writes, restart recovery, damaged-task isolation and stopping network activity when pause persistence fails.
- Real Ktor tests verify page-link traversal, resume through the actual remaining preview window, referrers, cookie isolation, site pinning and identity changes during an image response.
- Real file/Room tests cover reopen, failed atomic moves, same-size corruption and cancellation between image movement and metadata commit. Existing history, migration, preferences and native-driver regressions remain required.
- Reader tests cover local URI bounds and errors, cancellation, offline-to-online progress recovery and the original image/navigation behavior.
- Android instrumentation uses the production Rust decoder, real bitmap/files/Room and common UI with HTTP fixtures confined to `androidTest`. It pauses after one committed image, resumes without fetching it again, disables network access, reads saved pages, then closes/reopens the activity, queue and database and restores the saved page.

The updated source passed 94 network and 32 reader tests on Android/JVM/iOS, 22 Desktop and 16 iOS real-data tests, three actual iOS Keychain checks and both real application cold starts with the original gallery/account/history/browser/Rust checks. Full Android tests/lint/build passed 462 tasks; four APK signatures/ABI/16 KiB alignment, diagnostics and bytecode checks passed. The same updated APK pair passed all 38 instrumentation tests twice on each API36 phone and tablet without clearing device data. Independent test gallery identities and exact fixture/progress cleanup assertions repair repeat-run collisions. Earlier collision and concurrent-device UI failures remain recorded; sequential runs retained every test and the original timeouts.

Actual normal macOS ARM64 interaction completed a real 18-page Non-H gallery, opened saved pages 1 and 2, quit, and restored page 2 and its actual pixels in a new process from the same bundle and private profile. A previous build's profile separately resumed the same gallery from 4/18 to 18/18 and preserved completion across process restart, but reading its prior encrypted progress returned secure-storage failure after system-prompt handling. Its snapshot, keys and image files remain intact. Successful new-install recovery does not establish cross-binary Keychain access or repair that remaining issue. The earlier normal iPad run separately demonstrated complete download, offline pages, landscape, process recovery and foreground/background pause; no signed-device or manual airplane-mode claim is made.

Receipts and failures remain in `build/kmp-work-logs`; each pushed SHA receives its own required Actions results. Full packaged download/restart interaction on every architecture is still pending. Resume currently reuses completed pages; partial-image HTTP ranges, shared Rust archive import, remaining advanced media behavior and final platform integrations remain M4–M7 work. No version freeze, formal tag or production release is authorized by this slice.
