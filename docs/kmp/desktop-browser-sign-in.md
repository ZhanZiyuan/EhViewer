# Desktop native browser session handoff

This M3 slice connects the existing shared CMP Account controls to real desktop WebKit, WebKitGTK and WebView2 windows. Search, details and reader remain the same shared Kotlin/CMP implementation. Normal browsing uses real service responses; synthetic cookies exist only in explicit regression mode.

The Kotlin platform adapter calls Rust through JNI on Unix desktops and the existing owned-buffer C ABI on Windows. Rust owns a bounded private pipe to a native GUI companion, its main-thread event loop and process lifetime. Kotlin does not spawn processes or implement a second browser protocol. The companion uses an isolated nonpersistent store, the configured network User-Agent, system TLS, official service origins and the exact HTTPS Cloudflare challenge origin. Wry's portable navigation callback does not expose frame identity, so that challenge origin is allowed for navigation as well as subframes; its cookies are never transferred. Popups, downloads and permission requests are denied. No page evaluator, injected JavaScript or CAPTCHA solver is introduced.

Cookie transfer retains native domain spelling (including the leading dot), path, Secure, HttpOnly and expiry. Direct native cookie APIs avoid Wry's normalized domain accessor. The existing common transaction validates identity, scope, bounds and generation before one atomic encrypted-vault commit. Back or window closure discards the private store. Native handles have a separate numeric namespace, a four-process limit, bounded reads/deadlines and stale/double-close rejection. The parent library starts no background Rust reader thread: per-call Windows FFM arenas can close safely while the application keeps its main-thread DLL owner until all browser processes close.

`prepareNativeBrowser` compiles the actual distribution CPU with locked Cargo inputs and retains Cargo's executable receipt and SHA-256. The product resource merge keeps existing JNI/C ABI libraries and notices. Unix `jpackage` drops the executable bit of additional resources; the distribution task restores and checks that bit before DMG/image consumers run. Starting the browser after Compose commits also prevents an early native failure from being overwritten by the initial UI snapshot.

## Acceptance and remaining work

The explicit production JNI/C ABI regression launches two actual native browsers, reads each real cookie store twice, checks four metadata/isolation assertions, closes every process and rejects stale handles. Receipts bind native library/helper hashes, CPU and actual distinct PIDs; they contain no cookie values or credentials. All original archive ownership, image/gallery checks and Compose frame assertions remain mandatory. Host Linux/macOS JNI and installed Intel DMG (Rosetta and native Intel), Linux ARM64 image and Windows ARM64 image/extracted ZIP consumers require these additional proofs. Linux requires real WebKitGTK 4.1 >= 2.42 and Xvfb, without disabling its sandbox. Windows must provide its actual WebView2 runtime.

Local macOS actual JNI and C ABI calls passed: two native processes each, four native assertions per process, two reads each, zero remaining handles and stale-handle rejection. Real packaged Account → browser reached ready; confirmation without identity displayed the incomplete-login error, and Back returned to the guest Account and removed the owned child process. The UI tool cannot attach to this unbundled helper process, so visual inspection of its website window is not claimed. No live account identity or CAPTCHA was submitted. Actual Windows ARM64 MSVC compilation passed; native Windows/Linux runtime acceptance requires this SHA's hosted checks.

Local failures are retained in ignored `build/kmp-work-logs/`: initial JNI probe configuration-cache capture, an existing verifier task's script capture exposed by explicit cache validation, first packaged resource permissions/early Compose state, and an import-order check run before final formatting. Each requires a fresh passing rerun. No check is disabled or reported successful on that basis.

Final local checks passed: verifier 229 tests; original Android invocation 361 Gradle tasks in 3m14s including Release lint, four ABI and benchmark; actual APK/diagnostic/bytecode/source-policy checks; 4,170 JNI ownership assertions and 13 archive cases; real JNI packaged-browser transfer including abandoned-composition cleanup; real macOS C ABI transfer; strict macOS/Windows ARM64 browser Clippy and all three Android workspace Clippy targets. The explicit macOS C ABI probe does not claim Windows service lifecycle execution; that remains required on the actual Windows runner. M3 is still incomplete.
