## Reference and license decision

The read-only Animeko snapshot's `docs/contributing/architecture.md`, `app/shared/app-data/src/commonMain/kotlin/data/persistent/database/DatabaseStorage.kt` and the database/platform entries in `animeko-reference-audit.md` inform the separation of shared persistence from platform construction. Windows ARM64 compilation and execution require the actual Windows runner; local Kotlin task compilation does not establish success.

## Validation and limits

The first full history run exposed a packaging defect: the upstream SQLite JVM JAR contains Linux, macOS and Windows libraries for several CPUs, so the existing strict Linux ARM64 package scan correctly rejected foreign native bytes. `SelectDesktopSqlite` now selects the distribution target from the unchanged, SHA-256-pinned `sqlite-bundled-jvm` archive, preserving all non-native entries and the original license. It verifies the selected ELF/Mach-O/PE CPU before packaging. Windows ARM64 retains the upstream classes and license while using the separately built ARM64 JNI in `core/data`. Cache archives are never modified. Build-logic regressions cover byte preservation against the actual pinned upstream archive for every target, the missing Windows ARM64 upstream binary, wrong CPU, changed sources and invalid inventories/paths; the existing mandatory Android `:build-logic:convention:check` executes these tests. Existing package architecture checks and actual native database launches remain required.

The subsequent full run passed the Intel producer/native-consumer package checks, but the four standalone Desktop consumers could not resolve the task class from an unrelated plugin's classpath. The real `ehviewer.desktop.sqlite` convention plugin now registers this same configuration and dependency selection for both root and standalone builds. Validation includes the actual `./gradlew -p app/desktop` entry, native product/data tests and the root Android/desktop entries; neither task visibility nor architecture acceptance relies on a previous root build.

The next full run passed the actual Windows ARM64 SQLite tests and application image, then failed during the extracted ZIP's shutdown. Its original log identified `NoSuchElementException` while copying a concurrently shrinking browser-owner set. Registration, removal and the shutdown snapshot now share one lock; native cleanup happens outside it, and shutdown rejects new owners. The retained real browser bridge regression exercises 64 service lifecycles with 16 abandoned instances each, repeated closure and rejected registration after closure. The original native process, cookie, window, archive and timeout checks remain required; the failed SHA remains a failure.

The same full run executed the Windows ARM64 SQLite JNI and 17 real data tests, exposing two failed migration-file cleanup checks. The exact published Room 2.8.4 source (`BaseRoomConnectionManager.DriverWrapper`) opens a native connection before schema initialization; if initialization throws, that connection is neither closed nor admitted into the pool. The 2.8.5 stable patch retains this behavior, so an unrelated version change is not used as a repair. `OwnedRoomDatabase` independently owns the real driver alongside Room: normal pool closure runs first, then every remaining native connection is closed exactly once. Desktop/iOS application roots use this explicit owner; Android's original opening paths stay unchanged. The existing rollback and future-version tests retain their data/version and immediate file-cleanup assertions and additionally require zero owned connections after closure. No forced garbage collection, ignored Windows deletion error, delayed deletion, destructive recovery, Room fork or schema change is used.

- Four common Room tests execute real files, transactions, failure rollback and concurrent writes. Six JVM driver tests additionally exercise the underlying native engine's statement and transaction behavior.
- Three migration tests generate their historical SQL from the tracked version-17 schema, then verify the actual 17→18→23 migration, reopen, preserved downloads/favorites/progress, rollback after a failed migration, and refusal to replace a future-version database.
