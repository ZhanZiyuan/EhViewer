# Image-directory import in the shared reader

The local library now imports image folders into a private immutable snapshot and opens them through the existing `ArchiveDocument`, page provider and CMP reader. Desktop supplies a directory chooser; iOS uses the system folder picker, security-scoped access and coordinated reading until copying has stopped. Android retains its existing directory routes, with an explicit APK regression also exercising the common importer and real image decoder.

`ArchiveBook`'s serialized fields and existing compressed-book files are unchanged. A directory book has `pages.cbor` and opaque `image-<index>.bin` payloads; a compressed book retains `archive.bin`. Exactly one layout is required. The directory identity hashes a versioned manifest of ordered extensions, sizes and actual SHA-256 values, so reimporting identical images preserves the first title and reading-state identity. External paths and filenames are not persisted. The manifest and file metadata are checked on open; actual page bytes are hashed before delivery. Duplicate import also verifies existing payloads and never replaces corruption. Existing Rust archive sorting, encryption and JNI/C ABI remain unchanged.

Names are enumerated incrementally with Java NIO on Android/JVM and Kotlin/Native POSIX calls on iOS, with deterministic handle closure and a limit before another name is collected. The common traversal rejects symlinks and unsafe names, limits all entries to 100,000, depth to 32, accumulated relative paths to 4 MiB, images to 32 MiB each, total payload to 8 GiB and metadata to 16 MiB. Numeric runs are compared without integer conversion; ASCII folding and a lexical tie give uniform directory order across platforms. This independently implemented directory ordering leaves the existing Rust archive comparator intact. Header recognition precedes publication; the bounded existing image decoder validates pixels. No whole-process RSS or import-speed guarantee is claimed.

Copies stream in 64 KiB pieces and check cancellation, size and modification metadata. Atomic private-directory publication preserves existing books. Pre-publication cancellation/failure cleans the owned staging directory; a published book remains discoverable. A live reader's lease prevents deletion until admitted reads end. Failed payload deletion retains book metadata and allows missing payloads to be skipped on an explicit retry. Successful lease release also clears its strong document reference, so closed entries retained by the library cannot retain a large directory manifest. A regression inspects that actual ownership reference after close. Original user files remain untouched. Abrupt-process orphan staging cleanup and measured large-input performance remain hardening work.

Reference boundary: read-only Animeko `docs/contributing/architecture.md` and its previously audited platform/storage organization inform the separation of common behavior from platform access. Adopt that boundary, adapt it to EhViewer's private image manifests, archive leases and reader, and reject video/BT code, scripts and dependencies. No Animeko implementation or assets are copied. Main targets are `ArchiveLibrary.kt`, `DirectoryEntries`/`DirectoryImages`, `FileArchiveLibrary`, `ArchiveLibraryScreen` and the Desktop/iOS pickers. Kotlin platform APIs implement file enumeration and selection; no Swift, Objective-C, Java or C implementation is added. Apple's [directory access requirements](https://developer.apple.com/documentation/uikit/providing-access-to-directories) inform the iOS coordination/access lifetime.
