`verification windows-stage-zip --runtime-report REPORT --image IMAGE --output NEW_DIRECTORY` requires a clean, same-source successful Windows runtime report, both original measured UTF-8/Unicode/ownership/Compose launches and its unchanged independent JVM proof. It rechecks the complete native file set against the actual image, actual PE32+ ARM64 headers, native hashes and installed notice hashes. Launcher, bundled JVM, Skiko and Rust must all be present. Dirty CI trees fail; local packager dirty state remains explicit and distinct from the previously built clean input's state.

The Kotlin packager uses JDK ZIP APIs without additional dependencies or shell business code. It inventories every regular image file, rejects links/special files, path escapes, case collisions, input/output overlap and existing evidence, and writes an embedded source/version/runtime-proof manifest. The output parent must already exist; parent aliases are resolved before checking overlap, so a directory link cannot write the ZIP back into the image. The entire ZIP is then streamed back without extraction: exact entry set, bounds, CRC, every file size/SHA-256 and embedded manifest must match the complete measured image. This includes JARs, configuration and JDK/legal material in addition to Native files. It does not depend on Unix executable permission bits for Windows EXE launch semantics; it is not a generic Linux/iOS image packager.

The original native Windows runner still builds/tests Core and independent JVM FFI and launches the application image twice. ZIP creation is a new mandatory step in that same required job; a failure cannot pass the aggregate gate. A separate artifact retains the actual ZIP and complete package JSON. No original Native test, runner, timeout, Android step or production Release path is removed or changed. Actual ZIP extraction/launch and staged multi-platform aggregation remain subsequent independently gated work.

Adversarial Kotlin tests use actual compiler-generated class bytes and UTF-8 resources, then change/remove/add/rename payload entries, replace source receipts/inventories, inject traversal/absolute/drive/control paths and attempt evidence overwrite/input overlap. Fixtures prove byte-container rules only; real runtime evidence is separately mandatory. No new Animeko design/code/resource/script/dependency or third-party implementation is reused. The existing JDK/Windows/runtime licenses and incomplete SBOM audit boundary remain.
