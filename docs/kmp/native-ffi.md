# Rust FFI ownership

EhViewer retains its original Rust archive, image and protocol engine. `native/rust/src/ffi/native.rs` keeps the original Android JNI/direct-buffer surface. The portable registry in `native/rust/capi/src/lib.rs` and `archive.rs` supplies JNI consumers through `native/rust/src/ffi/jvm/archive.rs`, Kotlin/Native through `AppleArchiveFactory.kt`, and Windows JVM foreign calls through `WindowsArchiveFactory.kt`. No hand-maintained C, Swift or Java bridge is introduced; cbindgen and Kotlin/Native produce declarations from the Rust ABI.

## Borrowed calls and owned handles

C ABI input pointers are borrowed only for a call. Output slots are initialized on failure; panic boundaries return `EHV_PANIC`. Results are monotonic integer IDs, copied with the result length/copy/free contract rather than exposed Rust pointers. The result registry allows 4,096 buffers and 32 MiB of total owned result bytes; archive IDs occupy a distinct range starting at `1 << 60`. Stale IDs, cross-type IDs, null/oversized input and undersized output buffers fail explicitly. Error codes are defined in the C ABI source; Kotlin maps them to sanitized domain failures without exposing paths or credentials.

The archive registry admits eight sessions, limits page output to 32 MiB, accepts absolute UTF-8 regular-file paths of at most 65,536 bytes and rejects final symlinks. The original engine applies its archive/entry/count/decompression limits and natural ordering. Password bytes are bounded to 4,096 and temporary Kotlin arrays are cleared. Rejected passwords are an explicit unaccepted result, not a fabricated successful decode.

External files are copied, hashed, flushed, validated and atomically published before Rust receives a path. The private backing file must remain immutable while its handle or an admitted read exists. `ArchiveLease` rejects new calls after close, counts admitted calls and releases its real document only after they finish. Successful release clears its strong document reference. Library deletion refuses live leases. Shutdown waits before a Windows native owner can unload; one close failure is retained as a failure while other owners are still drained. Cancellation cannot skip shutdown cleanup. These are runtime ownership checks, not a claim that an unresolved close released its resource.

The original Android direct-buffer registry is a separate retained contract with its existing 128-buffer / 512-MiB budget, exact Java-object ownership and read-only buffer checks. Its limits must not be confused with the portable owned-result registry. Directory books use bounded private Kotlin files through the same document/lease contract; they do not invent a second native archive ABI.

## Execution and limits of evidence

Rust core/C ABI/JNI regressions cover real archive formats, Unicode, encrypted input, stale handles, corruption, budgets and concurrent ownership. Mandatory Android instrumentation uses actual packaged JNI, files, bitmap pixels and Room; packaged Desktop/iOS consumers import and reopen owned compressed files and directory images with real platform decoders. Explicit startup checks complete 2,000 Rust results per launch and require zero live results; archive consumers separately require zero remaining archive sessions. Actual memory ownership and admitted-read tests supplement those counters. They do not establish a whole-process RSS or large-library performance baseline.

Accepted results through `a6870162b` are recorded in the [ledger](ci-ledger.md). Directory `cf918f0c9` has its own required Full CI; subsequent recovery behavior has independent local/hosted acceptance in [local-library-recovery.md](local-library-recovery.md). Each receipt binds actual source SHA, architecture, binary hash and executed tests. A rendered probe, cross-compilation or ABI declaration does not establish a signed iOS device test or complete platform P0. Final eleven-package, minimum-system and performance acceptance remain separate requirements.

The boundary is independently implemented for EhViewer. Animeko's previously audited platform-interface organization is architectural reference only; no reference implementation, resource or dependency set is copied. Existing third-party libarchive/liblzma sources retain their pinned provenance and notices as described in [shared-archive-library.md](shared-archive-library.md).
