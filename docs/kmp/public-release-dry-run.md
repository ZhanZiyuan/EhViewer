# Secret-free release rehearsal

The original `releases.yml` prepare → matrix build → package → publish chain now covers the eleven required installation assets and has a separate manual, nonpublishing path. Its source-bound Release-workflow rehearsal must pass before this integration is accepted; PR-CI candidate preflight alone is insufficient. M5/M6 remain in progress until their other product, licensing and system requirements also pass.

Only `main` or `feature/kmp` can enter the manual dry-run. Feature runs require successful PR CI at the exact source SHA. They execute with read-only repository permissions. Every step referencing production signing secrets is restricted to publication from `main`; the write-permission publish job is skipped. Dry-runs neither create nor alter a tag or Release. Existing tags may belong to the stable version's earlier source; nonpublishing rehearsal does not assert ownership of them. Publication retains the original main-CI, ancestry, tag-conflict, retry and idempotence protections.

`public-release-dry-run-signing.json` is an intentionally public generated JKS test resource, including its public password. It is not a user credential and grants no service access. Its RSA-3072 certificate is pinned to `760b7ad9c5287d89f74602ecd934e7faee06d00db8f8d094d075ca64178d2822`, distinct from the unchanged original production certificate. The verifier checks actual keystore bytes and certificate DER. Public test signing requires an explicit mode plus the exact repository, workflow, event, branch and `publish=false` context. A local component test additionally requires `--local-component-test`, which is forbidden in Actions. Existing SNAPSHOT-only `--test-signing` behavior remains unchanged.

Dry-run APKs use the real optimized stable-version build, all four original ABIs and original identity/signature/JNI/alignment/diagnostic inspectors. Their manifests explicitly identify public-test mode; neither default production verification nor publication accepts these manifests. These APKs cannot update a production-signed installation. They are rehearsal artifacts, not production releases.

Each Android producer creates a fresh private diagnostic encryption key in its owned runner directory. The actual mapping, native symbols and source manifest are encrypted with the original RSA-OAEP-SHA256/AES-256-GCM envelope. Dry-run decryption authenticates the bundle and compares every retained file hash. Aggregation requires that receipt to match the encrypted payload and source manifest. Only encrypted diagnostics and hash receipts are uploaded; plaintext/private keys are removed in the always-run cleanup. Original production diagnostics still use the configured production public key and retain their ninety-day encrypted-artifact policy.

The original four Android ABI jobs stay on Ubuntu x64. Seven additional matrix entries use the exact required native runners. Both DMGs are produced on macos-latest ARM64; Intel production requires Rosetta and is followed by a consumption-only macos-26-intel job using the identical DMG. This retains the original prepare → build(matrix) → package → publish backbone, with explicit Intel validation before package. Linux packages execute both extraction and real FUSE entry; both Windows CPUs execute Core/JVM tests, two original-image launches and two extracted-ZIP launches. iOS stages the actual optimized Kotlin/Native unsigned iPhone/iPad IPA. Existing native packagers are reused; unchanged technical spikes are not repeated locally.

The seven native packages share the exact same forty-eight CPU/format/source/version/launch/XML/ownership assertions as Full PR CI. The moved validation block was compared byte for byte, except five callback argument labels. Native parts must bind all fifteen evidence roles to seven correct target/runner/version/SHA records; the Intel consumer remains mandatory. Package validates every actual byte set and retains exactly eleven root-level installation files with SHA-256, plus encrypted diagnostics outside that asset set. It does not claim minimum-system, performance, complete SBOM or full product P0 acceptance.

The portable verifier is built and tested once in `prepare`, then shared by matrix/package/Intel-consumer jobs. Native consumers do not rerun its Linux-only offline protocol client. No tests are removed. Windows transport omits duplicate original/extracted runtime directory copies after their launch evidence is recorded; the verified ZIP, inventories, native Core/JVM/launch receipts and actual XML remain required. The publisher protocol regressions execute the actual workflow script and retain original tag races, nested tags, drafts, failures and payload-tampering cases, adding rejection of public-test manifests before any API call.

Implementation reuses EhViewer's existing signing, packaging and diagnostics verifiers. No Animeko implementation, scripts or dependencies are copied; the M0 reference/license boundaries remain applicable. Stable versions stay `1.15.10 / 180074`.

Validation and exact-SHA hosted results are recorded with the substantive implementation and in Actions Summary. A passing eleven-package rehearsal does not establish full product P0, minimum systems/performance, complete license/SBOM clearance, signed-device iOS acceptance, M7/M8 completion or permission to publish.
