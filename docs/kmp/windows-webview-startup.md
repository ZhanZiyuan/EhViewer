# Windows WebView2 startup message wait

Cover head `1d15ba631210c34b4322fb986c288d83a333dd62` failed its required Windows x64 packaged runtime in [PR CI41450827301](https://github.com/ZhanZiyuan/EhViewer/actions/runs/41450827301/job/125297730751). All other required platform jobs succeeded; the gate correctly failed. An independent [Full retest41455959086](https://github.com/ZhanZiyuan/EhViewer/actions/runs/41455959086/job/125316807251) reproduced the same failure on a fresh runner. Its source tree equals the PR test-merge tree. Both helpers reached `window-ready` but never `webview-ready`, then failed the existing cookie bridge and120-second launcher deadline. The browser sources and runner image version matched the previous accepted head. These are retained failures, not a successful retry or an established one-off infrastructure fault.

The locked Wry0.57.1 Windows constructor uses webview2-com0.39.1 `wait_with_pump`, which checks a channel before blocking in `GetMessage`. Microsoft documents that [GetMessage dispatches sent messages while waiting for a posted message](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessagew). A callback can therefore satisfy the channel while the surrounding message call still waits. This mechanism is consistent with the observations; the failed runner's native stack was unavailable, so that exact stack location is not claimed as measured.

The independent Rust repair creates an owner-thread timer only around Windows WebView construction. [SetTimer with no callback posts WM_TIMER](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-settimer), allowing the existing third-party wait to recheck completed callbacks. The guard cannot cross threads and removes its timer on success, failure or unwinding. Pending timer messages contain no Rust callback/pointer; [KillTimer may leave already queued messages](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-killtimer). The normal application event loop continues after construction without a recurring startup timer.

Both Windows architectures must run two real Win32 unit cases: an idle owner receives its exact timer message; an asynchronously completed channel returns through the actual third-party wait and the timer is removed. A test-only bounded fallback prevents a broken message wait from hanging the unit runner, and using that fallback fails the case. The verifier requires both actual test names plus the original navigation test before packaging. Existing real browser processes, metadata assertions, repeated cookie reads, stale handles, image/ZIP launch checks and all release protections remain mandatory. Production20-second IPC,15-second cookie callbacks,45-second fixture and120-second launcher deadlines are unchanged. Incognito, navigation, permission and TLS policy are unchanged; no dependency version, JNI/C ABI, signing or workflow structure changes.
