# Shared immersive reader

This M5 UI slice gives online, downloaded and archive reading the same full-window canvas and overlay controls. It retains the existing bounded image/page window, actual Rust decoding, cancellation and decoded-only progress persistence.

The reference is EhViewer `v1.15.10`, commit `423b8af13632896b55780783b54b5f720ec4c9dd`: `app/src/main/kotlin/com/hippo/ehviewer/ui/reader/ReaderScreen.kt` and `eu/kanade/tachiyomi/ui/reader/{ReaderAppBars,ChapterNavigator,PageIndicatorText}.kt`. The new common `GalleryReaderChrome.kt` follows the original default black canvas, initially hidden controls, small page indicator, two-line Material top bar and 200ms sliding bars. It removes the library's 1040dp cap/keyline while reading, without changing the composition slot or losing the surrounding page state.

Supported actions remain real: paged/continuous mode, RTL/LTR, bounded zoom/reset and display/original image selection. The seek slider resolves real page tokens; it never saves a requested position before the image decodes. Continuous seeking uses the existing page window and keyboard-dismiss restoration. Center taps and Space toggle controls; edge taps use the current validated previous/next links. Existing keyboard paging remains, and continuous reading gains viewport-sized Up/Down/PageUp/PageDown scrolling. The page indicator supplies a localized accessibility action to reveal the controls.

The original orientation/crop/settings controls, configurable reader backgrounds, focused-control keyboard shortcuts, wheel/trackpad zoom and complete gesture/settings parity remain further work. This is not a claim that the entire reader or M5 is pixel-equivalent. Android keeps its original reader and preferences adapter alongside this migrated route.

The next visual restoration follows the same tag's `ChapterNavigator.kt` and `ReaderAppBars.kt`: a rounded seek surface, 16dp phone/24dp expanded outer keyline, 16dp inner keyline and an 8dp image-visible gap above the separate bottom bar. The bar uses the original FlexibleBottomAppBar's 64dp minimum content height; its safe bottom inset is additional. Raw 1080×2400 phone images exposed the earlier 56dp candidate's 21px downward offset; that candidate remains retained rather than accepted as final geometry. Overlay opacity follows the selected application theme (90% dark/95% light), including Desktop/iOS overrides that differ from the OS theme. Existing page-jump, previous/next, continuous seeking and focused-keyboard callbacks remain unchanged; page-label placement and the original settings/orientation/crop actions still need parity work.

Actual common Compose pixels verify rounded corners, outer image visibility, the gap and the separate full-width bottom bar at phone/Desktop widths in both themes. Only alpha-compositing samples allow one 8-bit rounding unit; geometry checks and the independent whole-page Golden comparator retain exact pixels. This is not a relaxed whole-page acceptance threshold. Existing real pointer-drag, pending-resolution, large-font and keyboard tests remain in the suite. No Animeko implementation or dependency is copied.

The final 64dp candidate passes shared Desktop 127, Android host 67, iOS Native 79 and app unit 22 tests, Android lint/APK builds, both Apple links and macOS packaging. Phone and tablet each pass all 53 instrumentation cases without skips on the identical frozen APK pair. No Animeko implementation or assets were used. The added zoom/direction vector paths come from Google's Apache-2.0 Material icon data, consistent with the existing local icon collection: [zoom_out_map](https://github.com/google/material-design-icons/blob/master/src/maps/zoom_out_map/materialicons/24px.svg) and [swap_horiz](https://github.com/google/material-design-icons/blob/master/src/action/swap_horiz/materialicons/24px.svg).
